Executive summary

The latest branch is not ready for a real-Live mutation. It contains useful scene-audition scaffolding, but production TypeScript and Python disagree about the data shape, method routing, discovery interface, monitoring fields, and tool schemas. The new bridge is not loaded in the running Live process. Four Windows CI jobs also fail at the new ACL-hardening path.

The repository is nevertheless substantially ahead of where it started. The correct move is to preserve that foundation while temporarily stopping broad feature expansion. This is sequencing, not a reduction of the project’s long-term ambition: establish one trustworthy production path first, then expand it slice by slice toward the north star below.

Product context

Project north star: the one-stop Ableton MCP

This project exists because the Ableton MCP ecosystem is fragmented. Existing implementations demonstrate valuable individual ideas—audio taps and spectrograms, high-performance UDP control, XY controllers, extensible tool frameworks, OSC-native transport, or basic Live operations—but no single maintained project combines broad Ableton control, deep musical and audio intelligence, safe agent workflows, strong user experience, and first-class macOS and Windows support. The purpose of this repository is to become that coherent platform rather than another narrow collection of commands.

Long-term objective: build the most fully featured, thoughtfully structured, extensible Ableton MCP possible—one that gives an agent broad, truthful control over a Live instance while keeping the person operating the agent informed, in control, and safe.

Who it should serve

The product must work across the full range of Ableton users instead of assuming one fixed workflow:

  • Beginners and idea-first creators should be able to ask for a beat, arrangement, sound, or production starting point in natural language and receive a useful result without understanding every Live object or engineering detail.
  • Working producers should be able to iteratively build and edit Session and Arrangement content, instruments, effects, automation, routing, recording, and project structure while seeing clear previews and retaining control over consequential actions.
  • Mixing and sound-design power users should be able to inspect complete signal chains, compare project material with a user-supplied reference, generate bounded waveform/spectral/time-frequency evidence, diagnose why a mix lacks loudness or punch, and receive specific, verifiable adjustment suggestions.
  • Advanced electronic musicians should be able to request detailed MIDI sequencing, drum programming, rack and device work, plugin parameter editing, patch-design guidance, modulation, probability, microtiming, and performance control.
  • Live performers and technical users should eventually have low-latency, explicitly armed realtime control through appropriate mechanisms such as bounded events, UDP, OSC, XY surfaces, Max for Live, or published device parameters—with emergency recovery and no hidden authority.

Representative end-to-end experiences

The north star is defined by complete user journeys, not merely a large tool count. Examples include:

  • “Make me a compelling beat with these high-level rhythmic and production traits,” followed by visible planning, creation, playback, revision, and undo.
  • “Here is a short reference clip and a similar section of my project. Analyze my guitars and drums, compare their dynamics and spectral balance, show bounded visual summaries, and explain which parts of my signal chain are making my version less loud or punchy.”
  • “Using the plugins I already own, help me design a bass or pad with these described sonic qualities,” including topology discovery, published parameter control, safe audition, and before/after verification.
  • “Show me how to sequence these drums with this kind of density, microtiming, probability, variation, and texture,” producing editable MIDI rather than a static explanation.
  • “Diagnose this mix or performance setup,” using authoritative routing, device, automation, latency, clipping, playback, and—when explicitly available—audio evidence.

References to artists or songs should be treated as requests for high-level musical, timbral, rhythmic, or production characteristics. The system should help users learn and create without claiming exact replication, legal clearance, or access to protected expression.

Product principles

  • Comprehensive, but coherent: Session, Arrangement, clips, notes, audio, devices, racks, automation, routing, recording, Browser, projects, performance, analysis, and plugins should form one discoverable model.
  • User experience is part of correctness: tools need compact discovery, meaningful names, plans, previews, progress, confirmations, actionable errors, and recovery—not raw object mutation alone.
  • Safe by construction: audible, destructive, recording, routing, file, and realtime actions require bounded authority, exact targets, fresh state, idempotency, verification, and an independent stop/recovery path.
  • Truthful capability negotiation: unavailable or simulator-only behavior must remain unavailable; the server must never invent state or overstate what a Live version, plugin, platform, or adapter can do.
  • macOS and Windows are first-class: installation, permissions, paths, process behavior, Live versions, and tests must be designed for both rather than ported at the end.
  • Extensible boundaries: Remote Scripts, future Extension APIs, Max for Live, OSC/UDP, hardware, analysis workers, and plugin-specific integrations should fit stable contracts instead of accumulating one-off pathways.
  • Musically useful analysis: audio features must be bounded, privacy-conscious, independently validated, honest about standards, and connected to concrete project/device evidence.
  • Complete workflows over demos: each capability is finished only when a user can discover, preview, apply, verify, recover, and understand it through the packaged production path.

How the current finish plan relates to the north star

The phases in this document deliberately establish one secure read-only connection and one reversible scene audition before expanding breadth. That narrow milestone is the foundation the larger vision depends on: if the project cannot reliably discover, launch, verify, stop, and recover one scene in the real application, adding dozens of higher-level tools only multiplies unverified behavior. However, every later domain listed below remains part of the immediate finish definition. The phases are dependency gates inside one completion effort, not a suggestion to stop after a minimal viable product.

Scope and intent of that authorization

Blocking defects in iteration 13

These are code-level blockers, not requests for more platform breadth. The final safety audit ran before the graceful pause completed and added independent reproductions for the concurrency, timeout, replay, and recovery defects below.

P0Concurrent requests can launch or stop twice

Audition apply and stop inspect transaction state but do not atomically reserve it before awaiting dispatch. With bounded concurrent stdio handlers, two identical requests can both observe previewed and call scene.launch. The audit reproduced two launches from a Promise.all of identical applies. A per-transaction serialization/reservation state is mandatory.

P0A timed-out Python request can mutate Live later

The Python dispatcher times out its waiter but leaves the callback in the main-thread queue. Draining the queue later still executes the mutation after the caller has received failure and the TypeScript adapter has destroyed the socket. Queue entries need cancellable dispatch tokens and a final validity check on the Live thread before mutation.

P0Host-side audition guards can be bypassed

The authenticated wire exposes generic scene.launch, stop-all-clips, and transport.stop. Any authenticated client can invoke them without the host’s Set identity, recording, monitoring, quantization, output-safety, revision, ownership, and confirmation checks. The mapper must expose one purpose-specific guarded audition operation and recheck all safety data atomically on Live’s main thread; generic audible invocation must not be a production capability.

P0Crash/restart loses stop authority

Transactions, tokens, idempotency records, and playback ownership exist only in host memory. If the host crashes or reconnects after launch, a new host cannot prove ownership or use the old stop transaction, while a new preview refuses existing playback. The first safe mutation requires a bounded durable journal or a separately authorized, independently available emergency stop with fresh authoritative readback.

P0Production snapshot shapes do not match

apps/mcp-server/src/host.ts reads playing, arrangementRecord, sessionRecord, launchQuantization, firedTargets, and playingTargets from snapshot.set. The Python mapper places playback data in top-level snapshot.playback. A real bridge audition preview therefore fails before launch.

P0Track monitoring and playback ownership are not authoritative

The host expects inputMonitoring; Python emits monitoring. Python also does not yet expose authoritative per-track playing_slot_index and fired_slot_index in the snapshot. Real Live generally exposes playback through those track fields rather than synthetic Song-level target arrays. Until those indexes are translated into exact scene/slot references, launch verification and ownership-safe global stop cannot be trusted.

P0Registry and mapper disagree about session.playback

The canonical registry declares session.playback as a discovery operation requiring revision, transport, firedTargets, and playingTargets. Python handles it through the invoke path and returns a different shape. A matching registry hash currently does not prove runtime payload compatibility.

P0The shipped production adapter cannot delegate discovery

The host conditionally calls discoverAsync, but RemoteScriptLiveAdapter does not implement that method. It falls back to a narrow snapshot-derived path. Host kind names are hyphenated while Python kind names are underscored, so an explicit translation layer is also required.

P0Advertised MCP schemas contradict runtime requirements

  • outputSafety advertises an object with no allowed properties while runtime requires safe and provenance.
  • The stop tool advertises confirmation literal "stop", while runtime requires the unpredictable stopConfirmation token returned by preview.
  • Schema-driven clients cannot correctly construct the documented workflow.

P0Real/fake provenance is not truthful yet

The Python status currently reports fake-live provenance unconditionally. Package smoke needs explicit fake provenance, but a loaded Control Surface in real Live must report a separate verified provenance without allowing a fixture to promote itself to real Live.

P1No production cross-process audition journey

The installed-package smoke authenticates and discovers a fake scene, but does not exercise set → tracks → clip slots → playback → preview → launch → verify → stop → verify through the packaged CLI and production Python listener. Unit tests exercise host logic against controlled adapters; they do not prove the actual production boundary.

P1Cancellation and deadlines are incomplete

The remote adapter uses per-request timeouts that destroy the session, but does not carry an AbortSignal and absolute deadline through discover/get/set/invoke. For a mutation, cancellation before dispatch must be distinguishable from uncertain state after dispatch.

P1Replay protection resets on reconnect

Python creates fresh nonce and sequence state for each client connection. The audit replayed the same authenticated launch frame through two connections and both were accepted. Replay state must be bound to the bridge epoch/session and old authenticated frames must remain invalid after reconnect.

P1Secret permissions are diagnostic-only

The production CLI reads a secret file without enforcing owner-only permissions. A mode-0644 secret was accepted in the audit. Permission validation must gate startup, not merely appear in diagnostics.

P1Launch verification is too weak

The host accepts set.playing === true as successful launch evidence even if no fired or playing target identifies the audition scene. Arrangement playback or an external transport start can therefore be misclassified as ownership. Only exact fresh scene/slot evidence may verify launch.

P1Safety and transaction state are unbounded

Several transaction maps, idempotency maps, stdio pending collections, and retained safety objects lack hard bounds or complete expiry eviction. Long-lived operation must cap and evict all records without discarding active recovery authority.

P1Documentation overstates what is connected

Several guides present guarded scene audition and expanded hierarchy as current production functionality even though the production adapter cannot reach the expanded mapper path and the snapshot shapes are incompatible. Recovery text also confuses exact idempotent replay with a separately authorized recovery stop.

What was wrong with the previous runs

  1. The goal was unbounded. “Comprehensive Ableton platform” included Session, Arrangement, audio, warp, takes, automation, routing, Browser, projects, Max/OSC, realtime control, accessibility, installers, signing, notarization, creative journeys, and real-Live evidence. That is a roadmap, not a single autonomous completion condition.
  2. The loop optimized breadth instead of the nearest testable milestone. Every iteration repeated planning, an exhaustive use-case scan, four implementation specialists, integration, review, validation, benchmarks, documentation, PR handling, five audits, and three final reviews. This spent hours repeatedly rediscovering known missing product areas.
  3. The Live gate is circular. The workflow renders the Live-test plan and approval only when validation.passed === true. Validation remains false because real-Live and production journey evidence are missing. The missing evidence therefore prevents the step that could create the evidence.
  4. Unrelated release gates blocked the first Live milestone. Coverage measurement, Windows ACL certification, UI/accessibility evidence, broad capability completeness, final-release review, and real-Live evidence were all mixed into one readiness decision. None should block a read-only bridge handshake.
  5. “Node finished” did not mean “finding accepted.” The implementation review finished with passed=false and ten remediation IDs. The documentation review then found ten more actionable inconsistencies. The workflow still moved forward because completion of review tasks was structurally different from satisfying their findings.
  6. Remediation was not closed before checkpoint. The bounded remediation fixed only a subset of review findings. There was no mandatory review-remediation-review loop proving every P0/P1 item closed before commit.
  7. Checkpointing occurred before external CI and final audit acceptance. Iteration 13 was committed and pushed even though local validation explicitly said required categories were unavailable and the docs review said production claims were not truthful. The resulting checkpoint then broke all four Windows Node jobs.
  8. Fake evidence accumulated faster than production evidence. The test count and package checks increased, but the actual new adapter was never installed into Live. This made progress look numerically strong while the critical end-to-end path remained untouched.
  9. The run had no practical escalation milestone. Once a running Live process was detected without a bridge configuration, the correct action was to surface the exact setup question and pivot to a narrow connection test—not continue dozens of broad iterations. That ambiguity is now resolved: the user has declared this Mac mini and its Live Beta environment disposable and granted standing mutation authority.
  10. The budget was far too large. At iteration 13 of a possible 50, the workflow could have consumed roughly 37 additional passes. Given the external and circular gates, more runtime did not imply convergence.
Conclusion: the agents were not primarily failing to write code. The orchestration was asking them to solve the whole roadmap before validating the first real boundary, and its gate topology made that boundary unreachable.

Definition of the immediate comprehensive finish line

The feature branch is complete only when the platform—not merely the bridge—satisfies the following evidence-backed conditions.

Production foundation and safety

  • PR #1 is synchronized to the exact reviewed SHA and every required CI check passes.
  • The canonical operation registry, TypeScript adapter, host, Python mapper, package manifest, and runtime payload validation agree exactly.
  • The authenticated bridge is loopback-only, secret permissions gate startup, replay is impossible across connections/epochs, and fake provenance cannot become real-Live evidence.
  • Concurrent duplicate requests dispatch at most once; timeout and pre-dispatch cancellation fence delayed callbacks; post-dispatch ambiguity becomes explicit uncertain state.
  • Audible/destructive safety is enforced at the Live-thread mutation boundary and cannot be bypassed through a generic operation.
  • Bounded durable recovery or independently authorized emergency-stop authority survives disconnect, timeout, acknowledgement loss, and host restart.
  • Installed-package cross-process journeys cover success, replay, stale state, external edits, partial failure, compensation, shutdown, and recovery.
  • The new bridge is tested in a disposable real Live Set with authoritative discovery, bounded mutation, verification, stop, restoration, and no residual state.

Comprehensive Ableton control

  • Session and Arrangement expose authoritative navigation plus guarded lifecycle editing for tracks, scenes, slots, clips, locators, selections, transport, loop, launch, capture, and recording.
  • MIDI supports complete note lifecycle and negotiated advanced expressive/probabilistic fields; audio supports source identity, fades, gain, pitch, looping, warp, and supported take/comp workflows.
  • Clip, device, mixer, and Arrangement automation/modulation are discoverable, editable, revision-bound, and recoverable.
  • Devices, racks, chains, drum pads, macros, variations, parameters, sidechains, latency, presets, and supported lifecycle operations are represented as one coherent hierarchy.
  • Browser search/filter/preview/load and third-party published-parameter/preset workflows are production-tested and capability-aware.
  • Routing, mixing, monitoring, arming, recording, sends, returns, groups, cue, sidechains, and transport are guarded against recording, feedback, clipping, and external-edit hazards.
  • Project and file workflows provide safe new/open/save/save-as/backup/collect/export/bounce behavior with allowlists, atomicity, rollback, and manifest verification.
  • Subscriptions, Max for Live, OSC, UDP, XY, and realtime control are authenticated, bounded, measured, short-lived, recoverable, and truthful about delivery.

Audio intelligence and complete user journeys

  • A consent-bound Live audio tap provides bounded capture and teardown without retaining or exposing raw audio unintentionally.
  • Waveform, spectrum, spectrogram/time-frequency, phase, transient, dynamics, loudness, loudness range, and true-peak outputs pass independent fixtures and applicable standards.
  • User-supplied reference comparison performs bounded alignment and level matching and connects measured differences to authoritative signal-chain evidence.
  • Natural-language beat/song creation, advanced drum sequencing, native/plugin sound design, Session/Arrangement editing, signal-chain diagnosis, mix/reference, recording, and safe-performance journeys work end to end through the packaged server.
  • Artist/song references are handled through rights-aware high-level musical and sonic traits without claiming exact replication or legal clearance.
  • Every consequential journey provides discovery, plan, preview, impact, exact confirmation, progress, postcondition verification, idempotency, undo/compensation, and residual-state recovery.

Cross-platform product readiness

  • Install, activation, upgrade, repair, rollback, and uninstall are tested on supported macOS and Windows environments and an explicit Ableton Live version/edition matrix.
  • The artifact includes the required host, bridge, registry, manifests, documentation, provenance, and legal/distribution metadata while excluding secrets, tests, local state, and protected SDK material.
  • Unit, property, integration, installed-package, performance, resource, security, recovery, accessibility, and real-Live gates pass against the exact release candidate.
  • Keyboard-only and screen-reader experiences are tested where applicable; known Live/plugin accessibility limitations are explicit and do not become fabricated support claims.
  • User, developer, operations, recovery, safety, compatibility, and capability documentation match observed implementation and evidence.
  • The version-controlled capability matrix covers every north-star domain and journey with no unresolved critical/high findings, placeholder implementations, generic contracts, or simulator-promoted claims.
Only when all four groups are satisfied is the immediate goal complete: a comprehensive, secure, extensible, cross-platform Ableton automation platform with deep musical/audio workflows—not simply a successful bridge smoke test.
